# Подключение Supabase

> Русский · [[docs/en/Backend Setup|English]]

2026-11-01 пользователь предоставил URL проекта и публичный publishable key. Они сохранены только в игнорируемом Git файле `.env.local`; существующий dev-сервер подхватил настройки. Read-only запросы Auth settings и таблиц fandoms/rooms вернули 200; Email включён, регистрация разрешена, подтверждение email обязательно. Это подтверждает доступность публичных API, но не выполнение каждой миграции и не права настоящих пользователей. Агент SQL в облаке не запускал. CLI supabase/docker/psql ранее не обнаружены в PATH.

Страницы `/signup`, `/login`, `/network` проверены в Chromium на ширинах 1440 и 390px: 200, нет сообщения об отсутствии конфигурации и горизонтального переполнения; поля пароля активны. Письма, настоящая регистрация, recovery и несколько клиентов ещё не тестировались. Используем стандартные письма Supabase.

## Облачный проект

1. Создать отдельный Supabase project для разработки; выбрать регион и сохранить пароль БД вне репозитория.
2. В SQL Editor выполнить целиком, по порядку, `supabase/migrations/20261101000100_foundation.sql` и `supabase/migrations/20261101000200_fandom_seed.sql`. Для уже используемой БД сначала сделать backup и проверить миграции на отдельном проекте. Эти начальные миграции не предназначены для повторного применения к существующей схеме.
3. В Auth включить Email и обязательное подтверждение email. Anonymous sign-in оставить выключенным, минимальную длину пароля задать 12 символов. Site URL для текущего локального приложения: `http://127.0.0.1:3000`. Разрешить redirect на `http://127.0.0.1:3000/auth/callback` и варианты этого callback с `next` для `/account`, `/join`, `/reset-password`. Для dev можно использовать `http://127.0.0.1:3000/auth/callback**`; не использовать wildcard-домены в production. Открытый внешний `next` приложение всё равно отклоняет.
4. По текущему решению используем стандартные письма Supabase: Email Templates и SMTP пока не менять. Код уже поддерживает PKCE `/auth/callback`; подтверждение и восстановление открывать в том же браузере и на том же устройстве, где начат запрос, сохраняя адрес `127.0.0.1`. Новый пароль задаётся только после подтверждения recovery-сессии. Кастомные HTML в `supabase/templates/confirmation.html` и `recovery.html` оставлены для будущего подключения; облачному проекту сейчас они не нужны.
5. Встроенная отправка Supabase предназначена для тестирования: без своего SMTP письма доставляются только на адреса участников команды проекта и действуют ограничения частоты. Для текущего теста использовать email владельца Supabase; для регистрации других пользователей позже подключить SMTP, сохранив стандартный дизайн писем при желании. Никаких писем агент в этой задаче не отправлял. SMTP-пароль вводится только в настройках Supabase, не в публичные переменные Next.
6. Скопировать `.env.example` в `.env.local` и заполнить три значения:

```dotenv
NEXT_PUBLIC_APP_URL=http://127.0.0.1:3000
NEXT_PUBLIC_SUPABASE_URL=https://PROJECT.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=YOUR_PUBLISHABLE_KEY
```

Можно использовать legacy `NEXT_PUBLIC_SUPABASE_ANON_KEY` вместо publishable key. **Service-role / sb_secret_ ключ приложению не требуется и в NEXT_PUBLIC-поле запрещён.** `DATABASE_URL`, SMTP и LiveKit также не нужны этому этапу. Секреты не коммитить и не отправлять в чат.

7. Перезапустить dev-сервер. Production использует Secure/HttpOnly/SameSite=Lax cookies и требует HTTPS. В dev допускается локальный HTTP. Публичные env должны быть заданы **до** production build; при смене конфигурации пересобрать приложение. Проверить `/network`, `/signup`, `/account`.

## Дополнение: стикеры и картинки

По просьбе пользователя облачные изменения отложены до следующей проверки. После двух начальных миграций выполнить **только** `supabase/migrations/20261101000300_chat_media.sql` в SQL Editor. Она добавляет media-поля, RPC и закрытый bucket chat-images (WebP, 384 КиБ) с RLS. Повторно запускать начальную схему или делать bucket публичным не нужно. У уже установленной базы проверить backup перед миграцией; новая миграция также выполняется один раз. Серверный код совместим со старыми текстовыми сообщениями; до миграции кнопки вложений отключены.

После применения проверить двумя подтверждёнными аккаунтами: стикер, JPG/PNG/WebP до 2 МБ, превью, просмотр картинки вторым участником, удаление сообщения и объекта, отказ новому запросу картинки после kick и невозможность загрузки в закрытую комнату. Прямые Storage-запросы также должны соблюдать RLS. Тесты локально используют storage-schema shim, Sharp и моки SDK; реальное облачное Storage пока не проверено. Подробности — [[docs/Features/Chat Media]].

## Локальный Supabase при наличии Docker

Конфигурация подготовлена в `supabase/config.toml`. После установки официального Supabase CLI и Docker из корня проекта:

```sh
supabase start
supabase migration up --local
supabase status
```

Перенести локальные URL и публичный ключ из вывода status в `.env.local`, используя тот же `127.0.0.1` для приложения и auth redirects. Локальные письма проверяются через Mailpit/Inbucket на порту 54324. Команда `db reset` удаляет локальные данные, поэтому здесь не используется как обычный шаг настройки. Остановку общего dev-сервера выполнять только владельцу процесса.

Эти команды в данной сессии не выполнялись: Docker/CLI отсутствуют. PGlite нужен только для изолированных SQL-тестов, не заменяет Supabase Auth/PostgREST.

## Проверки перед принятием серверного этапа

- [ ] Зарегистрировать два тестовых аккаунта, подтвердить email, проверить ошибку до подтверждения и успешный вход после.
- [ ] Проверить истёкшую/повторно использованную ссылку, recovery, смену пароля, выход и refresh сессии.
- [ ] Сохранить профиль и интересы, выйти и войти с другого устройства.
- [ ] Создать публичную и приватную комнату; второй аккаунт не видит приватную без допуска.
- [ ] Принять fragment-приглашение через вход, написать сообщение с другого клиента; сообщения обновляются каждые 3 секунды.
- [ ] Исчерпать/отозвать/просрочить приглашение. Сохранить только hash в базе; не возвращать token_hash через Data API.
- [ ] Удалить участника, проверить отказ чтения/записи и повторного входа, включая прямые REST/RPC-запросы. Проверить moderator/owner границы, выход и закрытие комнаты.
- [ ] Испытать параллельный redeem последнего допуска и конкурентный chat rate limiting на настоящем PostgreSQL.
- [ ] Проверить RLS advisors, кэширование авторизованных страниц, логи без credentials, Auth rate limits и SMTP.

Realtime, голос, аватары и global moderation не включены в готовые capabilities. Возможности плеера зависят от источника — [[docs/Features/Room Player]]. Сайт не публиковался.

## Дополнение: комнаты фандомов

После начальных foundation и fandom_seed применить один раз supabase/migrations/20261102000400_room_fandom.sql. Она независима от chat_media, добавляет rooms.fandom_id и меняет сигнатуру create_room на семь аргументов. До применения новый код создания общих комнат несовместим со старым RPC. Существующие комнаты не удаляются и не привязываются автоматически. Принимается отдельно двумя аккаунтами; агент облачную SQL-миграцию не выполнял. См. [[docs/Features/Fandom Rooms]] и [[docs/Fandom Sources]].

## Дополнение: плеер и общий источник

Голос подключается отдельно: LiveKit Cloud, voice-миграция и планировщик описаны в [[docs/Voice Setup]]. Публичного Supabase key для этих серверных операций недостаточно; секреты не передавать в чат.

Выполнить один раз supabase/migrations/20261102000500_room_player.sql поверх foundation-схемы. Она добавляет source_updated_at и RPC set_room_source, не меняет RLS и не требует media/fandom-полей. Если ранее не применены room_fandom/chat_media, они остаются отдельными шагами. До новой миграции просмотр уже сохранённого поддерживаемого URL доступен участникам, а форма смены источника отключена. Агент миграцию в облаке не применял. Принять owner/moderator/member и замену плеера двумя настоящими аккаунтами. Общая пауза/seek пока отсутствуют. См. [[docs/Features/Room Player]].

## Дополнение: сброс роли при повторном входе

Выполнить один раз supabase/migrations/20261104000700_rejoin_role_reset.sql поверх foundation-схемы; она не зависит от media/fandom/player/voice-миграций. Миграция добавляет триггер: вышедший или удалённый участник всегда возвращается обычным участником, и бывший модератор не получает права модерации обратно незаметно. Существующие данные не меняются. В облаке пока не применена — [[docs/Features/Server Rooms]].

## Дополнение: индекс для ограничения частоты сообщений

Выполнить один раз supabase/migrations/20261104000800_message_sender_index.sql поверх foundation-схемы. Она только добавляет индекс `room_messages_sender_recent`, чтобы ограничение «одно сообщение в секунду» оставалось быстрым по мере роста истории чата; схема и права не меняются. На небольшой тестовой базе это мгновенно; на большой production-таблице выполнить команду как `CREATE INDEX CONCURRENTLY` вне транзакции, чтобы не блокировать запись в чат даже ненадолго — [[docs/Features/Room Chat]].

## Дополнение: общий просмотр YouTube

Выполнить один раз supabase/migrations/20261104000900_room_playback.sql после foundation и room_player (она сравнивает с rooms.url и использует те же роли). Миграция добавляет таблицу room_playback с RLS и без прямых прав, а также get_room_playback/set_room_playback. Без неё комнаты сохраняют независимое воспроизведение, ничего не ломается. Принять двумя подтверждёнными аккаунтами: владелец запускает, ставит паузу и перематывает; участник следует, в том числе в браузере, запрещающем автозапуск — [[docs/Features/Shared Playback]].

## Дополнение: сигналы Realtime для комнат

Выполнить один раз supabase/migrations/20261104001000_room_signals.sql после foundation (и после 0900, если используется общий просмотр; её триггер добавляется только при наличии room_playback). В панели Supabase оставить Realtime включённым и разрешить публичный доступ к каналам (настройки Realtime), потому что канал сигналов публичный и не содержит данных. Без этого ничего не ломается: записи проходят, клиенты возвращаются к опросу. Проверить двумя браузерами: сообщение или пауза ведущего должны появиться в другом окне примерно за секунду — [[docs/Features/Room Chat]].

## Дополнение: очередь комнаты

Выполнить один раз supabase/migrations/20261104001100_room_queue.sql после foundation и room_player (0500). Если сигналы комнат (1000) применены раньше, изменения очереди тоже отправляют сигнал Realtime. Без этой миграции вкладка «Очередь» скрыта. Проверить двумя аккаунтами: участник добавляет ссылку, владелец включает её следующей, а окончание синхронизируемого видео включает следующую ссылку — [[docs/Features/Room Queue]].

## Дополнение: общий браузер (Hyperbeam)

Создать аккаунт Hyperbeam и API-ключ (проверить текущие цены; сеанс ограничен 4 часами и завершается через 5 минут простоя). Положить ключ в окружение сервера как `HYPERBEAM_API_KEY` (никогда не NEXT_PUBLIC, не в чат и не в Git) и перезапустить сервер. Выполнить один раз supabase/migrations/20261104001200_room_browser.sql после foundation (и после 1000, если нужны сигналы Realtime). Без ключа или миграции переключатель «Плеер | Браузер» скрыт. Проверить двумя аккаунтами: владелец открывает сайт и управляет им, участник только смотрит; удаление участника завершает сеанс для всех — [[docs/Features/Shared Browser]].

## Дополнение: аватар и обложка

Выполнить один раз supabase/migrations/20261104001300_profile_media.sql после foundation. Миграция добавляет приватный бакет profile-media с политиками, столбцы картинок в profiles и расширяет видимость любимых фандомов до владельца и его соседей по комнатам (то же правило, что и у профиля). Без неё на странице аккаунта просто нет редактора картинок. Проверить двумя аккаунтами в одной комнате: каждый видит аватар, обложку и фандомы другого; третий аккаунт вне комнаты не видит ничего — [[docs/Features/Profile Media]].

## Дополнение: друзья

Выполнить один раз supabase/migrations/20261104001400_friends.sql после foundation. Миграция добавляет заявки, дружбу, блокировки и журнал заявок с RLS и расширяет видимость профилей на друзей. Без неё /friends показывает прежнюю страницу-макет. Проверить тремя аккаунтами: заявка, принятие, просмотр профилей друг друга; блокировка с одной стороны — вторая сторона больше не может отправить заявку; третий аккаунт не видит ни одного из списков — [[docs/Features/Friends]].

## Дополнение: опыт, уровни и достижения

Выполнить один раз supabase/migrations/20261104001500_progression.sql после foundation и room_player (0500); после 0900 и 1400, если используются общий просмотр и друзья, чтобы их награды подключились. Позже балансировать через таблицу `xp_rules`. Проверить двумя аккаунтами: ежедневный визит начисляется один раз, вход в комнату открывает «Первые шаги», 15 минут в комнате дают опыт за участие — [[docs/Features/Progression]].
