# Активация музыки

> Русский · [[docs/en/Features/Music Activation|English]]

## Зачем нужна
Подготовить хранилище публичных чартов и еженедельное обновление с повторяемой проверкой готовности. Публикация чартов, импорт провайдеров и живая приёмка комнат проверяются отдельно.

## Пользователи и роли
Владелец применяет SQL и настраивает серверные секреты и GitHub. Доверенная еженедельная задача записывает публичные снимки чартов. Посетители могут только читать их.

## Пользовательские сценарии
Запустить проверку, применить оставшуюся миграцию чартов, проверить права, заполнить хранилище, проверить чтение без входа и после отдельного разрешения опубликовать и вручную проверить workflow.

## Правила поведения
`npm run music:check` делает только GET-запросы к настроенной таблице чартов. Выводит названия проверок и безопасные пояснения, без ключей, треков и тел ошибок удалённого сервера. Код 0 означает наличие актуальных проверенных снимков, доступных публичному клиенту; код 1 — незавершённую активацию. `--json` возвращает тот же безопасный отчёт.

`--for-publish` проверяет чтение таблицы издателем перед первым заполнением. Пустая таблица допустима, публичный ключ в окружении планировщика не обязателен. Эта проверка **не доказывает права записи**, работу провайдеров и расписания GitHub. SQL для владельца проверяет права без записи снимков.

## Интерфейс и состояния
До готовности облака приложение использует проверенный встроенный каталог. Для глобальных Spotify/YouTube и списка наиболее прослушиваемых требуются по 150 актуальных записей. Частичный чарт SoundCloud из США и недоступный TikTok остаются явно обозначенными ограничениями.

## Техническая реализация

### 1. Проверить готовность
Из корня проекта:

```sh
npm run music:check
npm run music:check -- --json
```

Реальная проверка только на чтение 2026-11-08: проект, публичный и серверный ключи настроены, но таблица чартов отсутствует. Ключей импорта YouTube, Spotify и SoundCloud нет. Запись в базу не выполнялась.

### 2. Однократно применить миграцию 23
В существующем проекте [Supabase Dashboard](https://supabase.com/dashboard) откройте SQL Editor и выполните именно `supabase/migrations/20261108002300_music_discovery.sql` из репозитория. Затем от имени владельца БД выполните `supabase/tests/music_activation.sql`. Скрипт в транзакции только для чтения проверяет RLS, публичное чтение, отсутствие прав записи у клиентов и права издателя, а затем показывает количество треков.

Возможности музыкальных комнат из миграции 22 уже представлены в облаке. Старые миграции повторно не применять. Если таблица уже существует, выполните проверочный SQL вместо повторного CREATE TABLE. История SQL Editor не равна истории CLI: перед дальнейшим развёртыванием через CLI согласуйте её по [инструкции Supabase](https://supabase.com/docs/guides/deployment/database-migrations#diagnosing-and-fixing-sync-errors). Эта подготовка не отмечает миграции применёнными удалённо.

### 3. Заполнить и проверить чарты
Следующие команды **записывают публичные снимки рейтингов** серверным ключом; запускать после применения миграции владельцем:

```sh
npm run music:check -- --for-publish
npm run music:refresh -- --database --no-write
npm run music:refresh -- --database --no-write --all-time-only
npm run music:check
```

`--no-write` отключает изменение встроенных JSON, но `--database` по-прежнему пишет в Supabase. Команда для наиболее прослушиваемых публикует проверенный встроенный список. Если его дата проверки старше восьми дней, сначала выполните `node scripts/build-music-chart.mjs`, который проверяет все 150 записей. При ошибке команды следующие шаги не выполнять.

Итоговая проверка валидирует все пять записей провайдеров и фактическое чтение публичным ключом. Три основных чарта должны содержать по 150 треков с проверкой не старше восьми дней. Затем откройте `/music` и страницу песни. После изменения переменных окружения перезапустите сервер; снимки из таблицы читаются заново при запросах страниц.

### 4. Подготовить импорт провайдеров
Задайте секреты в `.env.local` или окружении production-сервера, затем перезапустите его:

| Возможность | Настройка | Что ещё проверить |
| --- | --- | --- |
| Публикация чартов | `NEXT_PUBLIC_SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` | Миграция 23, права, заполнение и публичное чтение |
| Показ чартов | `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` либо старый `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Тот же проект; чтение после заполнения |
| Публичные плейлисты YouTube | `YOUTUBE_API_KEY` | Включение YouTube Data API v3 и реальный плейлист |
| Публичные подборки SoundCloud | `SOUNDCLOUD_CLIENT_ID`, `SOUNDCLOUD_CLIENT_SECRET` | Разрешённая публичная подборка через официальный API |
| Альбомы / старый адаптер Spotify | `SPOTIFY_CLIENT_ID`, `SPOTIFY_CLIENT_SECRET` | Доступ провайдера и реальный разрешённый альбом не проверены |
| Текущий API плейлистов Spotify | Авторизация пользователя, владение или совместный доступ | Пользовательский OAuth не реализован; ключей приложения недостаточно |

[Настройка YouTube](https://developers.google.com/youtube/v3/getting-started) описывает включение API и создание ключа. Учитывайте ограничения ключей для серверных запросов. Для новых учётных данных приложений [SoundCloud требует Artist Pro](https://developers.soundcloud.com/docs/api/register-app); покупка или регистрация не входят в подготовку. Существующие ключи используются через официальный [обмен client credentials](https://developers.soundcloud.com/docs/api/guide#authentication).

Spotify заменил пути плейлистов `/tracks` на `/items`; содержимое доступно авторизованному владельцу или соавтору. Текущий адаптер использует старый путь и ключи приложения. Его mock-тесты не доказывают живую работу. До объявления поддержки нужен разрешённый OAuth пользователя и обновление адаптера; доступ к произвольным публичным плейлистам не гарантирован. См. [миграцию Spotify](https://developer.spotify.com/documentation/web-api/tutorials/february-2026-migration-guide) и [текущий endpoint](https://developer.spotify.com/documentation/web-api/reference/get-playlists-items). Виджеты одиночных треков и опубликованные чарты не зависят от ключей импорта.

### 5. Подготовить еженедельную задачу
Публикация требует отдельного разрешения. Когда workflow окажется в основной ветке репозитория, включите Actions и задайте секреты репозитория:

- Обязательные: `NEXT_PUBLIC_SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`.
- Необязательные: `SOUNDCLOUD_CLIENT_ID`, `SOUNDCLOUD_CLIENT_SECRET`.

Ключи импорта YouTube/Spotify относятся к серверу приложения, а публичному обновлению рейтингов Kworb не нужны. Workflow сначала запускает `music:check --for-publish`, затем публикует снимки источников, перестраивает все 150 наиболее прослушиваемых песен и публикует этот список. Git push из задачи не выполняется.

Один раз выполните **Actions → Weekly music charts → Run workflow**, проверьте все шаги, затем локальный `npm run music:check` и `/music`. Расписание — понедельник, 06:00 UTC (07:00 по Варшаве в ноябре). GitHub запускает расписание из основной ветки и может задерживать его; локальная проверка не подтверждает удалённые секреты и успешный запуск. См. [расписание GitHub](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule) и [секреты Actions](https://docs.github.com/en/actions/how-tos/security-for-github-actions/security-guides/using-secrets-in-github-actions).

## Данные и доступы
`src/lib/server/music-readiness.ts` проверяет конфигурацию, доступ к таблице, снимки и публичную видимость. `scripts/check-music-setup.mjs` читает окружение загрузчиком Next и собирает проверку через esbuild. Новых таблиц приложения и зависимостей нет. Серверный секрет нельзя помещать в переменные `NEXT_PUBLIC_`; см. [типы ключей Supabase](https://supabase.com/docs/guides/getting-started/api-keys).

## Безопасность и приватность
Проверка готовности и проверочный SQL не меняют данные, не запрашивают OAuth-токены и не обращаются к музыкальным провайдерам. Команды заполнения и еженедельная задача отдельно обозначены как запись. Права обеспечиваются миграцией 23 и существующей авторизацией комнат.

## Критерии приёмки
Unit-проверки охватывают отсутствие конфигурации, привилегированный публичный ключ, отсутствие и пустоту таблицы, актуальные/старые/неверные снимки, скрытые от публичного клиента записи и безопасный вывод ошибок. SQL обнаруживает права записи у клиента и не меняет снимки. Токены, реальный импорт, два аккаунта и расписание требуют живой приёмки по [[docs/Acceptance Checklist]].

Локальная проверка: lint, typecheck, 361 unit-тест в 58 файлах, документация (156 заметок / 77 языковых пар) и production-сборка успешны. Новые инструменты не добавляют UI; предшествующие изменения загрузки прошли 27 затронутых desktop/mobile-проверок с одним намеренным пропуском на телефоне. Ненулевой код живой проверки означает ожидаемое отсутствие миграции, а не успешную активацию.

## Ограничения и следующие шаги
Обновление [[docs/Features/Music Player]] добавляет повторяемое исследование SoundCloud/трендов перед weekly-публикацией. Обе подборки хранятся в существующем payload `spotify-all-time`; дополнительных миграций сверх 23 не требуется. Встроенный каталог работает без облачной активации.

Локальная подготовка завершена; применение миграции 23, ключи провайдеров, OAuth Spotify и опубликованный успешный workflow не считаются выполненными. Remote push и применение SQL не выполнялись.
