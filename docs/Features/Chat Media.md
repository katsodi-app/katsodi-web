# Стикеры и лёгкие картинки в чате

> Русский · [[docs/en/Features/Chat Media|English]]

## Зачем нужна
Добавить эмоциональные сообщения без тяжёлых файлов и публичных ссылок на приватную переписку.

## Пользователи и роли
Только подтверждённые активные участники комнаты. Автор, владелец или модератор удаляет сообщение по прежним правилам.

## Пользовательские сценарии
Выбрать один из восьми SVG-стикеров, увидеть превью и отправить. Либо выбрать картинку, проверить превью, убрать или отправить её. Вложения отправляются отдельными сообщениями, без подписи; набранный текст сохраняется в поле для следующей отправки.

## Правила поведения
Исходник: JPG, PNG или WebP, до 2 МиБ и 16 миллионов пикселей, без анимации. Сервер читает реальные байты, удаляет метаданные, исправляет ориентацию и сохраняет WebP до 384 КиБ, не больше 1280×1280. При необходимости уменьшает до 960/640px. SVG/GIF и файлы с поддельным MIME не проходят декодирование. Весь multipart-поток ограничен 2 МиБ + 64 КиБ служебных данных, в том числе без Content-Length.

## Интерфейс и состояния
Кнопки стикеров и картинок, сетка восьми котиков, предпросмотр, удаление вложения, pending и локализованные ошибки. Кнопки активны только после положительного chat_media_capabilities; без миграции остаётся доступен текст. Состояние capability проверяет схему и настройки bucket, а не гарантирует доступность сервиса Storage.

## Техническая реализация
Миграция `20261101000300_chat_media.sql` добавляет тип сообщения и приватный bucket chat-images с лимитом 393216 байт и MIME image/webp. send_room_sticker/send_room_image используют существующий send_room_message: общие блокировки комнаты, проверка membership и лимит 1 сообщение/секунду. POST /api/rooms/[roomId]/images проверяет Origin, авторизацию, членство, размер потока и Sharp-декодирование. GET /api/chat-images/[messageId] заново проверяет доступ, загружает через Storage SDK и перекодирует даже загруженные вне формы файлы. В локальном config.toml Storage включён; в облаке миграция агентом не применялась.

## Данные и доступы
room_messages.kind = text/sticker/image; sticker_id либо image_path/image_width/image_height/image_bytes. Путь: roomUUID/userUUID/randomUUID.webp. Bucket приватный, UPDATE/upsert не разрешён. INSERT только в свой путь активной открытой комнаты, чтение только участникам (собственный orphan также доступен автору, orphan комнаты — активному владельцу/модератору для очистки). Удаление объекта — только после удаления ссылки из сообщений и своим автором либо активным модератором/владельцем. Порог 100 объектов на автора в политике загрузки — мягкий ограничитель, не строгая конкурентная квота.

## Безопасность и приватность
Никакого service-role. Подмена sender, чужого пути или произвольного sticker_id отклоняется. Лимиты размеров дополнительно заданы в bucket и CHECK-ограничениях. Публичных или подписанных URL нет; ответ изображения private/no-store, image/webp и nosniff. Новый запрос после kick не читает вложение; уже полученные байты невозможно отозвать. Автор может сохранить полученную картинку как любой контент переписки.

## Критерии приёмки
Изолированный PostgreSQL проверяет миграцию, RLS, запреты анониму/чужому/неподтверждённому/удалённому участнику, paths, размеры, повторное использование, rate limit и запрет замены. Storage tables в тесте — shim: реальный gateway и байты проверяются отдельно после подключения. Unit-тесты декодируют реальные растровые файлы и проверяют API с моками Supabase. Браузерный стенд не отправляет настоящие сообщения в облако.

## Ограничения и следующие шаги
Завтра применить только новую миграцию после двух существующих и проверить два аккаунта, загрузку/просмотр/удаление, kick, превышение размера и закрытую комнату — [[docs/Backend Setup]]. При ошибке публикации или удаления приложение пытается удалить orphan через Storage API; неудачную очистку и старые orphan необходимо обслуживать отдельно. SQL не удаляет storage.objects напрямую. Видеофайлы, GIF, произвольные стикерпаки, подписи и автоматическая фоновая очистка не реализованы.
