# Чат комнаты

> Русский · [[docs/en/Features/Room Chat|English]]

## Зачем нужна
Переписываться между настоящими участниками.

## Пользователи и роли
Активные участники читают/пишут; автор удаляет своё сообщение, владелец/модератор удаляют сообщения участников.

## Пользовательские сценарии
Войти в общую комнату, отправить сообщение до 2000 символов, увидеть переписку другого клиента, удалить сообщение.

## Правила поведения
Отправитель определяется только по auth.uid(). Сообщения доступны исключительно активным участникам, включая публичные комнаты. Закрытая комната не принимает новые сообщения. Базовый интервал отправки — 1 секунда.

## Интерфейс и состояния
Последние 100 сообщений, хронологический порядок, plain text, composer, pending/error, скрытие данных при отзыве доступа. Новые сообщения прокручиваются в видимую область, только если читатель внизу списка или сам отправил сообщение; того, кто читает историю, вниз не утаскивает. Время указано в UTC. Новый интерфейс — [[docs/Features/Room Experience]]; стикеры и сжатые картинки после дополнительной миграции — [[docs/Features/Chat Media]].

## Техническая реализация
room_messages и SQL-функции send_room_message/delete_room_message. **Сигналы Realtime (миграция 20261104001000_room_signals.sql):** триггеры БД отправляют пустое событие `changed` в публичный канал Realtime `room:<id>` при изменении сообщений, участников, просмотра или источника. Браузер (`src/lib/room-signal.ts`, без сессии) лишь сразу обновляет комнату через защищённый API, поэтому изменения должны доходить примерно за секунду (ещё не измерено: живой Realtime требует облачного проекта); текст сообщений, личности и состояние через Realtime не передаются. Знающий UUID комнаты может увидеть, *когда* она меняется, но не *что* изменилось. Без Realtime клиент опрашивает защищённый API каждые 3 секунды; при активной подписке опрос замедляется до 15 секунд как запасной вариант. Каждый запрос передаёт `?after=` с id последнего показанного сообщения, а сервер возвращает только упорядоченное окно id и полные строки более новых сообщений: тихая комната стоит одного index scan вместо повторной отправки 100 сообщений. Удалённые сообщения исчезают, потому что их id выходят из окна; несовпадающая дельта вызывает полную ресинхронизацию. Во скрытой вкладке опрос останавливается и сразу возобновляется, когда вкладка снова видна. Опрашиваемый endpoint проверяет JWT сессии локально (`getClaims`), не обращаясь к Auth-серверу каждый раз; членство и подтверждение email по-прежнему проверяет RLS. Ограничение частоты отправки использует индекс `room_messages_sender_recent` (миграция 20261104000800_message_sender_index.sql).

## Данные и доступы
В БД проверяется актуальное членство при каждом чтении и каждой мутации. Локальных выдуманных сообщений нет.

## Безопасность и приватность
React экранирует тело сообщения; клиент не задаёт sender_id. После kick чтение/запись отклоняются БД. Прекращение показа уже полученных данных происходит при следующей проверке.

## Критерии приёмки
RLS-тесты: outsider не читает/пишет, owner читает, kick отзывает доступ, close запрещает запись, rate limit работает.

## Ограничения и следующие шаги
Два реальных клиента, полный email-flow, большой объём и конкурентный rate limiting ещё не испытаны. Код вложений подготовлен, media-миграция и облачный Storage не проверены. Realtime WebSocket и полноценный anti-spam — будущие этапы.
