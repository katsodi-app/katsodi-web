# Installable Web App

> English · [[docs/Features/Installable Web App|Russian original]]

## Purpose
Lets a supported browser install Katsodi as an app (PWA): its own window and icon, the same website, the same sign-in as that browser. It is the light way to "install" Katsodi when a maintained browser is already on the device, with no second browser runtime. The separate Windows client is [[docs/en/Features/Desktop Application]].

## Users and roles
Every visitor. Installing changes nothing about accounts, rooms or permissions.

## User scenarios
- Chrome or Edge (desktop, Android): Settings → App → "Install Katsodi", or the browser's own install entry.
- iPhone and iPad: Safari → Share → Add to Home Screen (the page explains this; iOS offers no install prompt).
- Open the installed app without a network: a small Katsodi page says there is no connection and offers "Try again"; it reloads by itself when the connection returns.

## Behaviour rules
- The install button appears only when the browser really offered installation (`beforeinstallprompt`). Otherwise the section explains where the browser keeps it, or the iOS steps. No fake button.
- Shared rooms, chat, voice, imports and profile changes need the network. Nothing is queued for later and no multiplayer state is imitated offline. Local drafts stay in the browser as before.
- The service worker is registered only in production builds. In development it is not registered and an earlier registration is removed, so hot reload is never cached.
- Inside the desktop app the service worker is not registered (and an earlier one is removed): the shell has its own recovery screen, so there is one cache controller per environment.
- A new service worker version does not take over open pages: no `skipWaiting`, no `clients.claim`. It activates after every Katsodi tab and window is closed, never during a call, a screen share or an unsent form.
- No push notifications and no background sync: installing does not add a messaging backend.

## Interface and states
Settings → App shows one of: install button with a hint; "open as an installed app"; iOS instructions; "this browser is not offering installation"; or, in the desktop app, its version and a note that its sign-in is separate. The offline page uses the stored language and palette (all five palettes; System follows the device), the logo and Manrope.

## Technical implementation
- `src/app/manifest.ts` → `/manifest.webmanifest`: id `/`, start `/home`, scope `/`, `standalone`, Obsidian canvas colours, icons 192/512 and a maskable 512. `src/app/layout.tsx` adds the theme colour, the Apple touch icon and `appleWebApp`.
- Icons are derived from `src/app/icon.svg` by `npm run icons` (`scripts/generate-app-icons.mjs`) into `public/icons/` (and the desktop icons).
- `public/sw.js` (first-party, about 80 lines, no library): precaches `/offline/index.html`, two Manrope subsets and one icon in `katsodi-offline-v1`; answers a failed page navigation with the offline page; touches no other request.
- `public/offline/index.html` is generated by `npm run offline:build` from the `desktop` strings of `src/lib/i18n.ts` and the palettes of `src/app/signal.css`; a unit test fails when the committed file is stale.
- `src/lib/platform/install.ts` (install state, registration) and `src/components/platform-runtime.tsx` (mounted in the root layout).

## Data and access
Cache Storage holds four public files (one page, two fonts, one icon). No HTML of the application, API response, Server Action, RSC payload, script chunk, image, private media, auth callback, invitation or room snapshot is cached by the worker; those use the network and the browser's normal HTTP cache. Old `katsodi-offline-*` caches are removed on activation; no other storage is touched.

## Security and privacy
The worker handles only same-origin `GET` requests and only page navigations plus its own four files. Because it stores no personalised response, signing out or losing access leaves nothing behind in its cache. The existing Content Security Policy already allows a same-origin worker (`worker-src 'self'`). Cookie consent rules are unchanged.

## Acceptance criteria
- Unit tests (`tests/unit/platform.test.ts`): the precache list is exactly the four public files; no runtime caching, `skipWaiting` or `clients.claim`; a navigation falls back to the offline page; API, RSC, chunk, image, POST and cross-origin requests are left untouched; the generated offline page is up to date; both languages have the same keys.
- Checked in Chromium on a production build (`next start`, 2026-11-12): the worker registered with scope `/`; the cache held exactly the four files; the manifest served the expected identity and three icons; with the server stopped, opening `/home` showed the offline page in Russian with the Obsidian palette.
- Not checked: the browser's install dialog itself (it needs HTTPS or an interactive browser), installation on Android, iOS Add to Home Screen, behaviour across two deployments, storage quota errors and browser eviction.

## Limitations and next steps
A first visit without a network cannot work: the offline page exists only after one online visit. iOS has no install prompt and restricts some web APIs (screen capture in particular); those limits are the platform's. The manifest language and colours are fixed (Russian metadata, Obsidian); the pages themselves follow the user's choice. An "update ready" indicator is not implemented because the worker caches nothing that goes stale.
